# Candidate state simulation

`candidate-state.mjs` records untrusted candidate text as data, never as instructions. It has no CLI, executor, scheduler, network access, automatic resume, or paid calls. Use `node --test repo-ops/renewal/candidate-state.test.mjs` for the free simulation. Do not put secrets in candidate text, approvals, evidence, paths, or checkpoints; store files in a private local directory, not a published location.

`updateCandidate(file, event)` accepts one manually selected state file per task. Propose with `identity: { task }`, `receivedAt`, `project`, `source`, `original`, and a positive `maxAttempts`. The caller supplies the receipt time and original text; the model does not verify them. Worktree and session may be omitted at proposal; if supplied, they cannot change. `block_approval` records an unmet approval and a `reason`; starting remains prohibited. `approve` requires explicit `approval` and an identity with task, worktree, and session, fixing all three for subsequent events. `start` records the first attempt. While running, `checkpoint` stores an opaque checkpoint, `pause_rate_limit` records a specific `condition`, and `fail` or `complete` records an outcome. A manual `resume` requires the same condition and nonempty `evidence`, and consumes another attempt. An exhausted paused task stays paused; no automatic retry or reset exists. Completed and failed tasks are terminal. Duplicate start, proposal, or resume transitions are rejected.

The evidence is an operator's assertion, **not independently verified proof** of a real rate limit being lifted. Approval is also recorded text, not authenticated authorization. The caller must verify both externally and ensure the state path and identity correspond to the actual task, worktree, and session. Candidate text must never be evaluated as code or used as authorization.

Updates use an exclusive lock directory and a synced temporary file followed by rename. A crash may leave a lock or temporary file; the model refuses updates while the lock exists. Investigate the state and confirm no writer remains before manually recovering in a private directory. It does not sync the parent directory, authenticate state, protect against malicious filesystem changes, coordinate different state paths, or guarantee filesystem semantics across machines. A crash or power loss can leave an uncertain outcome. **Automatic execution is prohibited**: this simulation cannot guarantee durable exactly-once execution or safely coordinate real side effects. Never infer that a `running` record means work did or did not happen.
