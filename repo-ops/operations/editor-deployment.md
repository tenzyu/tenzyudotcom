# Editor deployment and rate-limit reference

## Application security

Editor mutations require the canonical `SITE_URL` origin in production or a server-configured `EDITOR_ALLOWED_ORIGIN` for an intentional preview or alternative endpoint. Without an override, development accepts only loopback HTTP. Forwarded client headers are not an origin or rate-limit identity. The limit of five attempts per minute applies within each process and is shared across clients. The process-local limit cannot enforce distributed limits and may deny legitimate logins during an attack. Session cookies are stateless and expire after 14 days. Rotating the signing secret invalidates them. Logout does not revoke a copied cookie. Actual deployment topology and distributed abuse prevention require operator verification.

## Vercel deployment policy

The owner's policy requires a single owner, a production-only editor, synthetic content only for non-production mutations, existing infrastructure, and stateless sessions. Vercel-hosted Preview and custom environments disable the editor and adapter mutation paths even if editor credentials are accidentally inherited. Synthetic write acceptance uses the existing isolated loopback Git fixture, not a live GitHub repository. No remote synthetic repository has been authorized. A public production build without Vercel system environment metadata denies editor access. The required Vercel settings are automatic exposure of system environment variables and `VERCEL_ENV` and `VERCEL_TARGET_ENV` both set to `production`. The owner explicitly permits **All Environments** credential scope. Application runtime guards do not isolate inherited credentials from untrusted preview build code or dependencies. All code receiving canonical write credentials must be trusted. Deployment Protection and automatic system-variable exposure remain operator verification items. No secret values or remote writes are required. Application code does not isolate untrusted pull request builds.

## External rate limits

Vercel WAF is the designated external rate-limit service. The owner did not authorize a separate application Redis service. On 2026-11-26 JST, the owner observed no recorded matches for the action-name selector. The selector for **Production**, `POST`, and a path ending in `/editor/login` recorded three requests in **Log** mode. The proposed final rule retains the path selector, uses a fixed 60-second window, limits requests to 10 per IP per region and returns HTTP 429. Matching alone does not establish enforcement. The synthetic regression in [workflow run 45739763640](https://github.com/tenzyu/tenzyudotcom/actions/runs/45739763640) reproduced successful Server Action dispatch from an unrelated page. Login now uses a form POST to the dedicated `/api/editor/login` Route Handler with same-origin validation and the existing rate limiter and session logic. The path suffix continues to match the new endpoint. Provider normalization, final publication, and enforcement remain unverified. Production load tests are not authorized. Logout remains a separate dashboard action. Rule availability and pricing require confirmation in the project dashboard. The code change does not authorize paid changes or firewall publication. Vercel counters apply per region. They do not enforce an exact global limit. The existing bounded process-local limiter remains a second control until provider enforcement is verified. HMAC cookies retain the existing 14-day time to live. Logout clears only the local cookie. Emergency revocation requires signing-key rotation and replacement or retirement of deployments that use the old key. The application does not guarantee per-session revocation.
